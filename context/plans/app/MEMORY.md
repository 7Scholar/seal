# Memory

## 2026-07-20 — Sealed format is standard age with an scrypt passphrase recipient

Sealed files are ordinary age v1 files with an scrypt passphrase stanza, and staying byte-compatible with standard age tooling is part of the design: any sealed file must remain recoverable with `age`/`rage` and the password alone, without Seal. **Why:** the format's value is that it is published, spec'd, and audited-in-practice, with a maintained Rust crate — not that its parameters are individually optimal. **Mistake it prevents:** "upgrading" the KDF to Argon2id (OWASP's first choice, which the landscape doc names) or adding custom header fields — either would silently fork the format and break standard-age recoverability; scrypt-not-Argon2id is deliberate, not an oversight.

## 2026-07-20 — The import scan must not respect gitignore rules

Scanning a repo for candidate secret files walks the tree with the ignore machinery **disabled**, pruning noise directories explicitly instead. **Why:** secret files are gitignored precisely because they are secret. Measured against a realistic repo, a scan using default gitignore-respecting settings returned only `.env.example` — the one file that is deliberately *not* a secret and is meant to be committed — while hiding all four genuine secret files behind the repo's own ignore rules. **Mistake it prevents:** enabling the ignore filters because respecting `.gitignore` is the obvious, idiomatic default for a repository walker, which silently inverts the import flow into proposing templates and concealing every real secret.

## 2026-07-20 — Directory pruning uses an explicit filter, never whitelist globs

Noise directories are excluded by filtering entries during the walk, not by adding positive include-globs alongside negative excludes. **Why:** override globs follow inverted-gitignore semantics, so introducing a single positive pattern makes everything not matching it excluded. Measured: combining a positive env-file pattern with a negated `node_modules` exclusion silently re-admitted a secret file under a build-output directory. **Mistake it prevents:** expressing the scan as "include these patterns, exclude those directories," which reads correctly, and fails in the dangerous direction — quietly widening the walk rather than narrowing it.

## 2026-07-20 — A test that needs a pseudo-terminal must skip on allocation failure, not fail

Tests that drive a real terminal — the CLI's password prompt and the interoperability suite, both of which spawn the stock binary through a pty — detect that no pseudo-terminal can be allocated and skip, except when the run sets the variable marking terminals as required, which continuous integration does. **Why:** checking only that `expect` or `script` is *installed* is not enough, because a sandboxed or container environment can have the binary present while `openpty` returns `Operation not permitted`. Without the distinction the suite fails for a reason unrelated to the code, which trains a reader to ignore a red run. The required-variable escape is what stops the skip from hiding a genuine breakage in continuous integration, where a pty is always available. **Mistake it prevents:** widening the guard to a bare skip so the sandbox stays green, which silently disarms the interoperability tests — the only evidence that Seal's format is compatible with the reference implementation.

## 2026-07-31 — `seal open` launches the binary beside itself before any installed one

The launcher's search checks for the application beside the running `seal` binary first, and only then asks the platform for an installed one. **Why:** the command-line tool ships inside the application bundle, so a `seal` run from within an installation must open the application it belongs to rather than a different copy the platform happens to have registered. In a source tree this same rule means `target/release/seal` opens `target/release/seal-desktop` — the build you just made — while a `seal` from elsewhere opens whatever is installed in `/Applications`, which may be far older. **Mistake it prevents:** "simplifying" the search to ask the platform first, which silently makes every `seal open` in a development tree launch the stale installed application instead of the current build, with no visible sign that it did.

## 2026-07-31 — `seal open` resolves its own path before looking beside it

The launcher canonicalizes `current_exe` before deriving the directory it searches. **Why:** the idiomatic way to put `seal` on a path is a symbolic link into `~/.local/bin`, and an uncanonicalized `current_exe` leaves the search rooted at the link's directory rather than the build it points at. Measured: through such a link the search walked into `target/release/bundle/macos/Seal.app` — a bundle that only refreshes on `tauri build` — so a plain `cargo build` left `seal open` launching a stale application while the binary beside the real target was current. **Mistake it prevents:** dropping the canonicalization as redundant, which silently reintroduces "the app opens an old version" for exactly the developers most likely to hit it.

## 2026-07-31 — A failed launch of a located application is not "not found"

`seal open` distinguishes an application it located but could not start (exit 1) from finding none at all (exit 9), and it silences the platform opener's own stderr rather than letting it through. **Why:** the macOS opener writes raw launch-services diagnostics to standard error and returns a non-zero status for both cases, so passing its failure through unmapped both leaks internal error text and tells a user with a correctly installed application that it is missing. **Mistake it prevents:** collapsing the two outcomes back into one, or dropping the stdio redirection because the opener "does not print anything" — it does, exactly when something has gone wrong.
