# Memory

## 2026-07-20 — Secret expiry never relies on a timer, and uses two clocks

A held secret expires by comparing deadlines when it is accessed, against **both** a wall-clock and a monotonic deadline, expiring if either has passed or if reading elapsed time fails at all. **Why:** the monotonic clock underlying ordinary timers **stops while the machine sleeps** — the platform documents this, and it was measured here as losing 7.26 hours across one night on the development machine. A timer would therefore keep plaintext alive through a closed lid and wake believing a minute had passed, which is precisely the situation a fifteen-minute expiry exists to prevent. The wall clock covers that, but it can be moved backwards by a clock correction or deliberately, so the monotonic deadline covers the wall clock in turn. **Mistake it prevents:** replacing the two-clock check with a single sleeping timer or a single clock, both of which look simpler, test fine on a machine that never sleeps, and fail open in the field — the worst possible direction for a security timeout.

## 2026-07-20 — The mutex-across-await check only arms once a command is registered

The compiler rejects a `std::sync::Mutex` guard held across an await in a Tauri command — but **only for commands registered in `generate_handler!`**. An unregistered command with exactly that defect compiles silently, because nothing yet requires its future to be `Send`. Verified both directions: the same code compiled clean unregistered and failed on registration with a message naming the guard and the await. **Why:** the `Send` bound lives on Tauri's async response path, which is reached through the generated handler, not on the command function itself. **Mistake it prevents:** writing a batch of commands, seeing a green build, and concluding the state handling is verified — then registering them later and being surprised, or worse, reaching for `tokio::sync::Mutex` to "fix" a problem the plain mutex never had. A command is not checked until it is wired into the handler.

## 2026-07-20 — Registry writes go through the store's update, never a snapshot store

Commands that change managed state call the registry store's compare-and-retry `update` and apply their change to the state it re-reads from disk, rather than calling `store` with the application's in-memory mirror. **Why:** the mirror the interface displays can be stale, and writing it wholesale silently discards anything another writer — the CLI, a second window, a concurrent operation — committed in the meantime. The revision check exists precisely to catch that, and passing a snapshot straight to `store` bypasses it. **Mistake it prevents:** "simplifying" a save to `store.store(&mirror)` because the application already holds the state it wants to write, which looks equivalent, passes every single-process test, and loses a user's registry entries under concurrency.

## 2026-07-20 — The session carries no deadline; only open files expire

The session holding the master password has **no** expiry of its own, while each open file's plaintext expires after an idle period that reading it refreshes. **Why:** what needs bounding is how long decrypted plaintext survives, not how long the user stays signed in. A session deadline adds no protection once every file's plaintext is already bounded, and it locks a working user out mid-edit, which trains them toward a longer expiry or a weaker password. The refresh-on-read is what makes the bound one on idleness rather than on total time open. **Mistake it prevents:** "hardening" the design by giving the session its own fifteen-minute deadline, which looks stricter, breaks continuous editing, and protects nothing the file deadlines do not already cover.

## 2026-07-20 — On macOS it is `Instant` that stops during sleep, not `CLOCK_MONOTONIC`

Rust's `Instant` is backed by `CLOCK_UPTIME_RAW`/`mach_absolute_time` on macOS, which **stop** while the machine sleeps. `CLOCK_MONOTONIC` and `mach_continuous_time` keep running through sleep and are **not** what `Instant` reads. Measured on the development machine in one reading: `Instant` and `CLOCK_UPTIME_RAW` both at 8.26 hours against `CLOCK_MONOTONIC` and `mach_continuous_time` at 15.52 — a 7.26-hour gap. **Why:** the naming is backwards from the intuition, since "monotonic" sounds like the one that would exclude sleep. **Mistake it prevents:** reasoning that `Instant` is safe against sleep because it is "the monotonic clock", or verifying the behaviour with a `CLOCK_MONOTONIC` probe, which measures the one clock that does *not* have the problem and appears to disprove it.

## 2026-07-20 — Wiping secrets happens on the exit request, never on a window closing

The explicit wipe of session and file secrets hangs off the application-level exit request, not off a window-close event, and is never left to values being dropped. **Why:** the normal quit path terminates the process without running destructors, so scope-based wiping silently never runs on the ordinary path; and the platform's quit shortcut can bypass window-close events entirely, so a wipe attached there does nothing for the most common way a user quits. **Mistake it prevents:** moving cleanup to a window event because that is where a window-shaped application seems to want it, or trusting a wipe-on-drop that never fires. Note that a force-quit runs nothing at all, which is why the expiry above must be short rather than merely present.

## 2026-07-20 — Only env files are editable, and the check is by name at the boundary

Opening a managed file yields an editable env view only when its name says it is an env file; everything else opens opaque, and reveal and save refuse it. `.envrc` is deliberately excluded despite the name, being a shell script rather than key-value lines. **Why:** the env parser accepts far more than env files. Measured before the guard existed: a Terraform `.tfvars` parsed into two editable rows, and saving rewrote `secret_key = "x"` as `secret_key="x"` — dropping the spacing and quoting HCL requires and silently corrupting a file the root intent says is stored as-is and never edited. The parser cannot detect this itself, because `key = value` is valid in both formats. **Mistake it prevents:** removing the name check as redundant because "the parser handles anything" or "a non-env file just yields no variables" — it does not; it yields plausible-looking variables for several real config formats, and the corruption only appears on save.

## 2026-07-20 — A repo password override is resolved by path containment, never by exact match

The session's per-repo overrides are keyed by repo root and resolved by testing whether a file path is inside that root, with the nearest enclosing root winning. **Why:** the root intent's model is one master password with an optional override **per repo**, so an override is set on a repo and must reach every file within it. An exact-key lookup — the obvious `HashMap::get(path)` — never matches, since the key is a directory and the lookup is a file, so every file silently falls back to the master password and is sealed with the wrong one. Verified before the fix: a file inside an override repo resolved to the master password with no error. Containment is tested on path components rather than string prefixes, so a sibling repo sharing a name prefix is not covered. **Mistake it prevents:** implementing or "simplifying" the lookup to an exact match, which compiles, passes any test that sets an override directly on a file path, and silently disables the feature in the only way it is actually used.

## 2026-07-20 — Seal never checks whether a file is open by scanning descriptors

There is deliberately no `lsof`-style check before sealing, and Seal never tells a user a file is safe to seal because nothing holds it open. **Why:** modern editors read a file into memory and close the descriptor immediately — measured, an editor with many workspace files open in tabs held a descriptor on none of them, only on its own indexes and settings. The whole dangerous sequence was then reproduced: editor reads and closes, Seal seals, the user presses save, the editor writes its in-memory buffer back and the secret is in the clear again. A descriptor check reports "safe" at every step of that. What Seal does instead is warn when a file was modified very recently, state in the warning that it cannot see an editor's unsaved buffer, and rely on reconciliation detecting a sealed file that became plaintext as the actual safety net. **Mistake it prevents:** implementing the "notice when a file is open in an editor" requirement as a descriptor scan, which is the obvious reading, looks rigorous, passes a test that holds a file open artificially, and produces a confident false assurance in precisely the case it exists to catch.
