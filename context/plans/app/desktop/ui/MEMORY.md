# Memory

## 2026-08-04 — The background re-observation poll swallows a locked session on purpose

`reobserve`'s caller catches every error and returns `null`, so a `locked` reported by the 5-second poll never reaches `relock`. It is the only caller that both checks the session and runs unattended. **Why:** the poll runs while the user is mid-task on a surface that holds unsaved work — the manage surface's selection, expansion and filter live in component state, and `relock` clears the overlay that holds them. Letting a background poll relock the window means a transient failure silently throws away work the user is in the middle of, with no act of theirs to explain it. A lock that actually matters still arrives through the command the user invoked: the confirm fails, `fail` sees `locked`, and the relock happens where the user can attribute it. **Mistake it prevents:** "fixing" the bare `catch` by routing its error through `fail` or `relock` — which looks like plainly correct error handling, matches every other call site, and is the one change that would make a live manage selection genuinely destroyable. Two tests in `App.test.tsx` name both halves of this rule.

## 2026-08-04 — A disclosure's Escape rule can only be tested by moving focus, never by clicking away

The check that a disclosure dismisses on Escape from outside itself moves focus with `element.focus()` and asserts the disclosure is **still open** before pressing Escape. It does not click the outside element. **Why:** an outside press dismisses the disclosure by the *other* rule, so a test that clicks away and then presses Escape is asserting against something already closed — it passes whether or not Escape works, for every disclosure in the product. Written the obvious way it did exactly that: three passed vacuously and the fourth failed on the focus assertion, for a reason unrelated to the divergence being closed. The intermediate "still open" assertion is what keeps the setup honest. **Mistake it prevents:** writing the natural click-then-Escape sequence, which reads like a stronger test than focusing programmatically and is in fact no test of Escape at all.

## 2026-08-04 — A row's height cannot prove its text truncated, because the row holds its height while the text overflows

A check that a name truncates rather than wraps measures **the name's own height against its line height**, and separately asserts the name is genuinely clipped (`scrollWidth > clientWidth`). It does not measure the row. **Why:** `.tree__row` carries `min-height` and `align-items: center`, so a wrapped name overflows the row's box rather than growing it — the row measures the same 30px whether its name is one line or three. A guard written against the row therefore passes with the truncation deleted, which is exactly what happened here. The clipped assertion is the second half for a separate reason: a fixture name that *fits* its column makes the check vacuous in the other direction, and only asserting the overflow makes that visible rather than silent. **Mistake it prevents:** writing the obvious "all rows are the same height" check for a truncation rule, which reads as a stronger assertion than one about a single element and is in fact no assertion at all.

## 2026-08-04 — `.visually-hidden` pins itself to the origin, because an unpositioned absolute escapes every scrolling region

The visually-hidden utility carries `top: 0; left: 0` alongside its clip. **Why:** `position: absolute` with no offsets resolves against the nearest *positioned* ancestor, and none of this interface's scrolling regions are positioned — so each hidden span lands at its own flow offset in the initial containing block, outside the region that was supposed to contain it. One span per row is invisible at ten rows and structural at four hundred: measured on the file surface at 400 variables, 394 escaped spans extended `documentElement.scrollHeight` to **26,695px in a 720px window**, and the document genuinely scrolled — `scrollTop` accepted 500 — while `body`, `.shell`, `.shell__main` and the surface itself all correctly measured 720 or less. The visible layout is right in every element that has a box, which is what makes this so hard to see: the only thing wrong is a stack of 1px clipped spans nobody can see. **Mistake it prevents:** dropping the offsets as redundant on an element that is clipped to nothing anyway — they are the only thing keeping it out of the document's flow height — or, on meeting the symptom, hunting the frame chain of a surface whose every element already measures correctly.

## 2026-07-31 — The toggletip claims `role="status"` only while it is open

The disclosure bubble's wrapper carries `role="status"` when open and no role at all when closed. **Why:** a live region that exists permanently on every disclosure means one surface carries as many status regions as it has explanations, and assistive technology then has several competing status sources — the same defect this plan group already caught once, when the unsaved-changes indicator and the reveal announcement both claimed one region. Here it surfaced as an ambiguous `getByRole("status")` the moment a batch-seal report shared a screen with a toggletip. **Mistake it prevents:** hoisting the role onto the always-rendered wrapper because a live region "should exist before the content arrives" — which is true for regions that announce updates in place, and wrong for a disclosure whose content only exists once the user asks for it.

## 2026-07-31 — Sidebar expansion and selection are separate, and deliberately so

Clicking a repository's name selects it; clicking its twisty expands it. Neither triggers the other, and the keyboard splits the same way — arrows move and expand, Enter selects. **Why:** conflating them makes two ordinary things impossible: reading a repository's summary while its file list stays collapsed, and browsing a file list without navigating away from what is currently open. **Mistake it prevents:** "simplifying" selection to also expand, which feels tidier, matches a naive reading of a tree, and fails the test that names the rule.

## 2026-07-31 — The unlock input submits on its own Enter keydown, not on implicit form submission

The hidden password input handles Enter in a keydown handler that prevents the default and submits; the surrounding form's submit handler is a backstop, never the mechanism. **Why:** synthesized key events — which is what the journey harness sends — are untrusted, and untrusted Enter never triggers a form's implicit submission in the real webview, so relying on the form alone makes the driven journeys hang at the first Enter while working fine under a human keyboard. The preventDefault is what stops a human's trusted Enter from submitting twice. **Mistake it prevents:** deleting the keydown handler as redundant with the form, which passes every unit test and breaks every automated journey.

## 2026-07-31 — The unlock shield types into a real, visually hidden password input

The unlock screen captures typing through an actual `<input type="password">` that is visually hidden, autofocused on mount, and refocused whenever it blurs — never through key listeners on the window or the canvas. **Why:** the real input is what keeps the labeled accessible name, the password-masking semantics, the autocomplete/spellcheck/autocapitalise opt-outs, and IME and dead-key composition working while nothing on screen looks like a form. The input is `readOnly` rather than `disabled` while the key derivation runs because a disabled input drops focus, and the screen has no other focus target to hand it back from. **Mistake it prevents:** "simplifying" the hidden field into a keydown handler, which silently breaks screen readers and non-ASCII passwords — or "restoring" a visible field because a hidden one reads as a leftover.

## 2026-07-20 — Revealing a value is not an edit, and the two use separate state

The environment editor keeps revealed values and pending edits in two separate maps, and only the edit map feeds the unsaved-changes count and the save payload. **Why:** reveal and edit are different operations on the same row, and conflating them corrupts dirty-state tracking. This is not hypothetical — a comparable product shipped exactly this bug when it added click-to-reveal, and its users hit a stale unsaved-changes counter telling them to refresh. Verified here: routing reveal through the edit map fails the two tests that name the rule. **Mistake it prevents:** merging the two maps because a revealed value and an edited value are both "the value for this row", which is true and still wrong — it makes merely looking at a secret mark the file as changed.

## 2026-07-20 — The reveal control's state lives in `aria-pressed`, never in its label or icon

Each reveal toggle is a `<button>` carrying `aria-pressed`, with an accessible name that is **constant across states** and **names its variable**, plus a live region announcing the change. **Why:** a screen-reader user cannot see the glyph, so state conveyed by icon alone is invisible to them — a real product shipped this defect on two clients, and separately shipped the eye icon inverted between two field types, which shows the glyph convention is not reliable even for sighted users. The name must carry the variable because every row has one of these buttons, and identical names leave a screen-reader user unable to tell which field they are toggling. **Mistake it prevents:** flipping the label between "Show" and "Hide" — which seems more informative and instead destroys the `aria-pressed` contract — or shortening the name to a generic one during a tidy-up.

## 2026-07-20 — The manage flow preselects only what the scan judged genuinely secret

The manage flow preselects candidates classified as secrets and nothing else; ambiguous files are shown unchecked and templates are shown unchecked. **Why:** the asymmetry of the mistake runs one way. A backup tool selects everything by default because over-inclusion merely costs storage. Here, managing a file that was meant to stay readable means encrypting it, which breaks the user's build with no obvious cause. Under-inclusion is a file the user adds later; over-inclusion is a broken repository. **Mistake it prevents:** adopting the select-everything default as friendlier, which fails five tests here and is actively harmful in this domain.
