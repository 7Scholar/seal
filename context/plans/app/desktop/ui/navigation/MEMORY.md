# Memory

## 2026-08-04 — A repository stops existing when its last file is released, so the files list has no reachable empty state

`lifecycle::release` drops the repository from the registry once `repo.files.is_empty()`, so releasing the last managed file returns the user to the repositories grid rather than to an empty files list. The other two ways in are closed too: the manage flow's confirm is disabled on an empty selection, and a rescan only ever adds. **Why:** this makes the empty-repository markup in the files surface unreached code that nonetheless reads as a live state in the plan, and the failure is silent in the direction that wastes time — driving it looks like the empty state is broken, when nothing ever asked for it. Measured by releasing both managed files in the running application and landing on the grid's empty state. **Mistake it prevents:** writing a test or a driven check for the empty files list and concluding the surface is defective when it never renders, or "fixing" the release path so a repository survives with nothing in it — which is a real product decision about what managing a repository means, and is open in `QUESTIONS.md` rather than settled.

## 2026-08-04 — A failed overview leaves the files list showing stale rows, because the refresh throws before reconciling

`refresh()` sets `load` to `failed` and **rethrows**, so `refreshAndReconcile` never reaches `reconcile` and `repos` keeps its previous value. The route stays where it was and the surface keeps rendering the rows it already had. **Why:** this reads as a working surface — the rows are all there and nothing errors — while the contents are whatever Seal last saw, after an operation the user just performed. It is reachable from every operation on the surface: sealing, batch sealing, saving and releasing all re-read the overview when they finish. The fix is a notice above the list rather than a replacement for it, because rows a user is told are stale are more useful than a blank screen. **Mistake it prevents:** treating a failed overview at this altitude as "the surface goes blank" and building a loading or error screen for it — the surface does not go blank, which is exactly what makes the defect invisible; and removing the notice as redundant because the grid already has an error state, which is a different state on a different surface.

## 2026-08-02 — The window controls are positioned in Rust, because `trafficLightPosition` is ignored

The traffic lights are centred against the strip by moving the three `NSWindowButton` views directly at setup (`titlebar.rs`), not by the `trafficLightPosition` window option. **Why:** that config option is read by the runtime but does not reach an `Overlay`-styled window created from configuration on this version — measured, setting it to `y: 17` left the buttons at their macOS default of 7px from the window top, an 8px error against a 46px strip, while its `x` did apply. The effective path in the runtime is `with_traffic_light_inset` on the *webview* attributes, which the config's window attributes never populate. The Rust code shifts both axes and derives the horizontal inset from the vertical one, which is the relationship macOS itself uses. **Mistake it prevents:** "simplifying" the Rust away in favour of the config option, which looks like the supported API, is documented as such, silently does nothing on the vertical axis, and leaves the buttons visibly high in the bar. Note also that the strip's height is duplicated as `STRIP_HEIGHT` in Rust and `2.9rem` in the stylesheet; changing one without the other un-centres the buttons.

## 2026-08-02 — The title bar drags because of `data-tauri-drag-region="deep"`, and CSS app-region does nothing

Window dragging is decided by a framework-injected script that walks the composed path of each mouse press; the CSS `app-region` property is **not** consulted, and this webview discards the declaration at parse time — measured, it does not survive into `cssRules` and reads back empty from `getComputedStyle` in both a working and a broken build. The strip carries the `deep` value because a bare attribute drags **only on a direct press of that exact element**, and everything a user presses in the strip — the breadcrumb trail, the current segment, the empty space — is a child of it. **Why:** the shipped strip had the bare attribute and looked correct in the markup while being dead everywhere a person would actually grab it. **Mistake it prevents:** "simplifying" `deep` back to a bare attribute because the bare form is what every example shows; or adding `-webkit-app-region: no-drag` rules for the strip's buttons, which is inert CSS that appears to be load-bearing — interactive children already exclude themselves, because the same walk stops at the first clickable element it meets.
