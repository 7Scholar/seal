# UX research: a file-tree picker surface with fixed chrome

Produced by following [the research procedure](../../../../../../../docs/UX_RESEARCH.md). This document is the design input for [manage-surface.md](../manage-surface.md). It sits beside [navigation-research.md](navigation-research.md), which holds the prior art behind the breadcrumb model and the repositories grid this surface must look like it belongs to.

It works **within** [repo-layer/adopting.md](../../repo-layer/adopting.md), which owns the tree's contract. That contract is settled, implemented, verified, and not reopened here. Where a finding from the prior art would violate it, the finding is refused and the refusal is recorded in Tier 3 with its reason.

# Concern

The surface a user meets when adding a repository to Seal or rescanning a known one. It draws the user's **entire repository** as a checkbox tree, with the files Seal detected as probable secrets already checked. The user reviews that proposal, adjusts it, and confirms. Confirming records what Seal manages; it **encrypts nothing** — sealing is a separate, deliberate act later.

This is the screen where a user decides whether to trust Seal with a credential, so its job is not merely to be usable but to read as **trustworthy and precise**. A surface that looks provisional at that moment fails at its actual job however correct its tree is. The product owner reviewed the running application and judged it *"written as a school project rather than a proper production ready UI"*, and named the target: *"the key features of production ready UI in 2026 is to show elegance and minimalism whilst having all the possibilities of managing whatever operation in the UI that you're seeing in front of you."* Those two pull against each other deliberately — the failure on one side is a cluttered panel, on the other a surface so spare the user cannot act.

## The constraints this design works inside

Settled by [adopting.md](../../repo-layer/adopting.md) and non-negotiable:

- **A folder's checkbox selects only the detected candidate files beneath it, recursively — never every file beneath it.** This is the invariant that guards against damage rather than confusion: sealing a file meant to stay readable breaks the user's build, and a recursive select-all is one careless click away from queueing a repository's entire source for exactly that.
- **Expansion and selection are separate axes.** Neither triggers the other. Conflating them means browsing a branch can queue files for encryption.
- **Expansion is computed on arrival** from the union of the ancestor chains of the preselected files. The window persists nothing, so every launch is a cold start and the view is identical on each one.
- **A collapsed directory renders none of its children.** This is what bounds a repository measured at 42,123 rows; a collapsed directory costs exactly one row regardless of what is under it. A tree that built every row and hid the collapsed ones with styling would pay the full cost invisibly.
- **Pruned and unwalked directories are inert, unexpandable rows.** They are drawn so the tree stays honest as a picture of the repository; they refuse to open so that honesty is not an invitation into `node_modules`.
- **The assistive-technology model is `aria-checked` only**, with `mixed` on partially covered folders and no `aria-selected` anywhere.

And from [the interface plan](../../README.md), binding on every proposal below:

- **Prose is a last resort, not a layout element.** If the interface needs a sentence to explain itself, the interface is insufficient. Full sentences are permitted in exactly two places: inside an **info affordance the user chose to open**, and in a **destructive-act confirmation**. This forecloses subtitles, ledes and helper text anywhere in this surface's layout.
- **The frontend never holds plaintext**, and this surface reads no file contents at all — it holds paths, structure and classification.
- **Friction is spent exactly twice**, and neither is here. Adding a repository gets no confirmation dialog: it encrypts nothing and is fully reversible.

## The family this must mirror

A breadcrumb-routed three-altitude navigation model: a **repositories grid** of tiles with a toolbar above it, a **files list** of large rows, and a **per-file editor**. The grid has just been carried to production depth and is the benchmark — it has every state designed, a fixed-height tile, a search field at a toolbar's leading edge, a skeleton loading treatment and an error state in the danger treatment. The shared visual language is four radius tokens (`--radius-sm` `0.5rem`, `--radius-md` `0.75rem`, `--radius-lg` `1rem` the default, `--radius-xl` `1.25rem` for large surfaces), semantic colour tokens throughout, and **two elevation levels only** — raised surfaces carry a border and no shadow, floating surfaces carry a tokenised shadow. There is an `Icon` component on a fixed `0 0 20 20` grid whose closed set already includes `chevron-down`, `chevron-right`, `search`, `check` and `plus`.

## What exists today, measured

The surface is [ManageFlow.tsx](../../../../../../../ui/screens/ManageFlow.tsx) over the tree primitive at [FileTree.tsx](../../../../../../../ui/components/FileTree.tsx). `ManageFlow` is now the **sole consumer** of `FileTree` — the steady-state managed view was rebuilt as large rows — so changes to the primitive carry no cross-surface risk.

Six structural facts, established from the source and the window configuration, that the design must answer:

- `.manage` is `max-width: 72rem` centred with uniform `1.6rem 1.75rem` padding, and `.tree` separately carries `max-height: 26rem` with its own `overflow-y: auto`. The window is **1100×720 by default, 800×560 minimum**. So at the default window the tree is given **416px of a possible ~622px** and wastes over 200px of height, while the 72rem cap exceeds the default window width and does nothing at all until the user has a wide display. The object the user came to work with is a small box in a column.
- The chrome is in normal flow — heading, path, tree, then a `<footer>` — so **Cancel, the confirm button and the repository identity all scroll away** on any repository whose tree is longer than the window, which is every real one.
- The surface returns **before the shell renders**. It replaces the entire window including the title bar, so it has **no breadcrumb, no theme control, no lock, and no `data-tauri-drag-region`** — the macOS traffic lights sit on bare content and the window cannot be dragged while it is open. It is not a modal in any technical sense: no `role="dialog"`, no `aria-modal`, no focus trap, no Escape.
- **A bare row click currently selects.** On a folder with candidates beneath it, clicking anywhere on the row toggles the selection of those candidates — this is asserted by tests. On a folder with **no** candidates, `candidates.length === 0` returns without acting and the row is also `selectable: false` so it draws no checkbox: the click is **inert**, with no expansion, no selection and no feedback, while `.tree__row` still sets `cursor: pointer` on every row including that one. Because the tree draws the whole repository and expansion is deliberately narrow, most folders a user sees are exactly this kind.
- **The scan is fully awaited before the overlay opens** (`startAdd` in App.tsx does `setOverlay({ name: "manage", scan: await ipc.scanFolder(root) })`). A loading state therefore **does not exist and cannot render** — the user stares at the previous screen for the duration of a scan measured at 42,123 rows. A failed scan never opens the surface at all and falls to the generic problem banner on the previous screen, so a scan-failure state does not exist here either.
- The only non-populated state that renders is `manage__empty`, a single grey sentence beside a tree — the same language mismatch the grid's rebuild removed.

# Sources surveyed

**VS Code's Explorer and Source Control view** — the reference implementation for a file tree with per-row state and bulk actions. It separates the two axes this surface needs to keep separate and gives each its own setting: `workbench.list.openMode` (`singleClick` default) governs *opening* an item, while `workbench.tree.expandMode` (`singleClick` default) separately governs *folder expansion*, and even under `doubleClick` expand mode a click directly on the twisty still expands on one click. Indent guides are `workbench.tree.renderIndentGuides` (`onHover` default) over `workbench.tree.indent` (**8px** default). `explorer.compactFolders` is **on by default**, compressing a non-branching chain into one row — and its interaction caveat is documented at length, because a compressed row's segments need per-segment click, rename, drag and multi-select handling. `workbench.tree.enableStickyScroll` is **on by default** with `workbench.tree.stickyScrollMaxItemCount` at **7**, pinning the ancestor chain of the topmost visible row and capping itself near 40% of view height. Ctrl/Cmd+F inside a focused tree opens a Find widget with an explicit **filter-vs-highlight toggle**: filter prunes the tree to matches keeping ancestors for context, highlight leaves everything visible and cycles matches. The SCM view stages via a hover-revealed inline `+` per row while a **row click opens the diff**, carries per-row single-letter status badges (M, U, A, D) in git decoration colours, offers `scm.defaultViewMode` (`tree`/`list`), and puts bulk actions such as Stage All Changes in the view's **title bar action area** rather than inline. Its extension API models checkbox trees as `TreeItem.checkboxState`, a state explicitly distinct from row selection.

**GitHub's file tree**, in repository browsing and PR review. Collapses **single-child directory chains into one compound row** (`foo/bar/baz`), the same affordance as VS Code's compact folders. A **"Filter changed files"** input matches on path segments rather than only the leaf name, and shows any file under a matching folder. The PR tree appears automatically only above two changed files and a sufficient window width. Per-row **comment, error and warning indicators** live in the tree rows themselves so a reviewer can find files needing attention without opening each diff. The **Viewed** checkbox sits on each file's header, collapses that file's diff, feeds a progress bar in the PR header, and **auto-clears with a "Changed since last view" badge** when the file changes underneath it. File headers **stick to the top of the viewport** while scrolling a multi-file diff. The 2026 rebuild made the tree panel resizable and added an experimental virtualization mode that explicitly disables in-browser Find — a stated cost of virtualizing.

**GitHub Desktop** — the closest analogue of all, and the one whose behaviour is confirmed at source level rather than inferred. A **row click selects the file for viewing its diff and does not toggle inclusion**; toggling inclusion from the row happens only for keyboard activation (Space or Enter), which is a separate code path from the mouse click. The checkbox is the only pointer affordance that changes what will be committed. The master checkbox is **genuinely tri-state**, with an explicit `Mixed` value used when some but not all files are included. The header reads `"N changed files"` (or `"M of N changed files"` while filtered) and deliberately carries **no selected sub-count** — a request to add one was closed. The commit button's template is `{Commit|Committing} {N file(s) }to <bold>{branch}</bold>`, so the button itself literally states the count and the destination: **"Commit 3 files to main"**. The commit message box and that button sit in a **fixed panel at the bottom** of the changes sidebar, below the scrolling list. The list is flat, not a tree; a tree view is a long-standing and heavily upvoted unimplemented request.

**Tower, GitKraken, Fork and Sublime Merge** — strong peers, corroborating the same split. Tower's per-file checkbox is a real tri-state: checked when fully staged, a visually distinct **half-checked** state when partially staged. GitKraken has **no checkboxes at all** — staging is a hover-revealed per-row button plus a bulk "Stage all changes", and **"Click a file to open its diff"** is documented outright, which is the cleanest confirmation that the row click belongs to *viewing* rather than to the operation. Fork exposes a first-class **tree/list toggle** on the file list. All of them dock the commit message and its button in a **persistent panel** separate from the scrolling file area. None of the four was confirmed to state a file count on the commit button, which appears to be GitHub Desktop's own refinement rather than a shared convention.

**macOS Finder list view and NSOpenPanel** — the native expectation this app's users arrive with. In Finder's list view a **single click on a folder row selects it and does not expand it**; the **disclosure triangle** is a separate hit target that expands in place; **Option-clicking** the triangle expands the whole subtree recursively; **double-click** opens the folder, replacing the window's contents; **Right Arrow** expands the selected folder without moving selection into it, and Left Arrow collapses. `NSOutlineView`, which Finder's list view is built on, documents the disclosure triangle as the expansion target distinct from the row's selection click. `NSOpenPanel`'s chrome is a toolbar and sidebar at the top and side over the browsing area, with a **fixed bottom bar carrying Cancel and the action button**, the action button rightmost and bound to Return, Escape dismissing. Its label is not fixed: the `prompt` property is explicitly customisable, so the native panel's own convention is that **the action button states what will happen** rather than saying "Open".

**Backup and sync selection trees** — Dropbox selective sync is a checkbox tree in a dialog where checking a parent includes everything nested inside it, applied by a fixed **Update** button; expansion is via the triangle beside the folder. Arq scopes its checkbox tree per backup folder, letting the user drill in and uncheck individual items within a folder it is backing up. The mixed/filled checkbox meaning "this folder is selected but something under it is excluded" is the standard hierarchical-partial-selection idiom across this category. Notably, **none of the surveyed sync tools was confirmed to show a running "N GB selected" total** — the blast-radius statement in this category is weaker than in the git clients, not stronger. Time Machine's exclusions are a useful negative: the most natively-macOS example in the set deliberately uses a flat add/remove list rather than a checkbox tree at all.

**Installer component trees** — the classic fixed-header / scrolling-body / fixed-footer shape. The Visual Studio Installer splits coarse "Workloads" from a fine-grained "Individual components" tree and keeps a **running total of required space** visible against the confirming action while the component list scrolls; the macOS installer's Customize pane is a genuine checkbox tree of choices driven by `choices-outline`. The durable lesson is the shape and the persistent running total rather than any particular control.

**W3C ARIA Authoring Practices — Tree View and Dialog (Modal)** — the invariants. On multi-select state: *"Some design systems use `aria-selected` for single-select widgets and `aria-checked` for multi-select widgets"*, and *"Conditions that would permit a tree to include both `aria-selected` and `aria-checked` are extremely rare. It is strongly recommended to avoid designing a tree widget that would have the need for more than one type of state."* Enter *"Activates a node, i.e., performs its default action. For parent nodes, one possible default action is to open or close the node."* Right Arrow *"When focus is on a closed node, opens the node; focus does not move"*; Left Arrow closes an open node, else moves to the parent. Home and End move to the first and last focusable node without opening anything. Space *"Toggles the selection state of the focused node"* in the multi-select model. The optional `*` *"Expands all siblings that are at the same level as the current node."* Typeahead is Recommended: *"Type a character: focus moves to the next node with a name that starts with the typed character."* The APG's examples document keyboard support only and state no mouse rule, but they hold **selection and focus as distinct** — moving focus does not change what is selected. For the modal: background windows are inert, Tab and Shift+Tab cycle within the dialog, **Escape closes it**, `aria-modal="true"` is only claimed when the background genuinely is inert, `aria-labelledby` points at a visible title, and for **high-consequence actions initial focus goes to the least destructive option**.

**Material and Apple on fixed chrome over a scrolling body** — both converge on the same treatment. Material specifies that a dialog's title and action buttons **stay fixed while only the middle region scrolls**, with a divider that appears between the content and the fixed chrome **only once content is actually scrolled underneath it**, rather than being permanent chrome. Apple's scroll edge effect is the same idea natively: *"a scroll edge effect provides a visual separation between certain interface elements, such as toolbars, and the scrolling content area behind them… replacing hard dividers with subtle blur to reduce clutter"*, with the **hard variant used mostly on macOS**, applied once per view, and explicitly *"not decorative"*. On macOS a sheet is always modal, and the confirming button sits **rightmost with Cancel to its left**, Return activating the default button and Escape dismissing.

**Nielsen Norman Group on response times** — the three limits that decide the loading treatment. **0.1s**: *"the user feel[s] that the system is reacting instantaneously… no special feedback is necessary."* **1.0s**: the limit *"for the user's flow of thought to stay uninterrupted"*, and below it *"it is distracting to use a looped animation, because users cannot keep up with what happened."* **10s**: the limit *"for keeping the user's attention focused on the dialogue."* Percent-done indicators are for operations over about 10 seconds; between roughly 1 and 10 seconds a lightweight busy indicator is right and a true progress bar *"would violate the principle of display inertia."* The convention for avoiding a flashed spinner — delay showing it by roughly 250–500ms so fast operations never show one — is a broad community practice rather than NN/g's own published number, and is flagged as such.

# Findings

## Tier 1 — table stakes

- **The row click must do something, and in a browsing tree that something is expansion.** Every source that draws a hierarchy gives the folder row a response: VS Code expands on single click by default via a setting that exists *separately* from the one governing opening; Finder selects on single click and expands on the triangle; nothing in the survey has a row that swallows a click silently. A row that draws `cursor: pointer` and then does nothing is the single most clearly wrong thing on this surface, and it is what most folders here do.
- **Fixed header, scrolling body, fixed footer.** Universal across the entire survey — every git client docks its commit panel, every installer keeps its footer, `NSOpenPanel` fixes its bottom bar, Material and Apple both specify it. The chrome scrolling away with the content is not a style choice this surface made; it is the shape nothing in the prior art uses.
- **The action button states the blast radius.** GitHub Desktop's *"Commit 3 files to main"* is the sharpest instance, `NSOpenPanel`'s customisable `prompt` is the native one, and the installer's running total is the same instinct. This surface already counts (`Manage N files`) and must keep counting — the count is the surface's whole safety statement, which is exactly why letting it scroll off is worse than cosmetic.
- **A separate, always-hittable twisty.** Finder, VS Code, Dropbox and every outline view give expansion its own target that works on one click regardless of what the row does. Required here anyway, since pruned rows must have no twisty at all.
- **Tri-state folder checkboxes.** Tower's half-checked, GitHub Desktop's explicit `Mixed`, and the hierarchical-selection idiom across the backup tools. Already built and already `aria-checked="mixed"`; the finding confirms the contract rather than changing it.
- **The row click never changes what the operation will act on.** GitHub Desktop routes the mouse click to viewing and inclusion to the checkbox in separate code paths; GitKraken has no checkbox and still reserves the row click for the diff; the APG holds focus and selection distinct. For this surface the stakes are higher than in any source surveyed, because the operation queues files for encryption.
- **Full keyboard operability against the APG's tree model** — arrows to move and expand, Space to toggle the focused row, Enter for the default action, Home and End, a roving tabindex, and a visible focus ring. Already built and carried forward.
- **Every state designed in the surface's own language.** The family rule, and the grid's rebuild is the in-house reference for it.

## Tier 2 — strong, high-value

- **A filter over the tree.** Table stakes in the two densest sources — VS Code's in-tree Find and GitHub's "Filter changed files" — and the deciding fact here is measurement rather than fashion: at 42,123 rows with expansion deliberately narrow, a file the scan did not detect is reachable only by manually opening the chain to it. Without a filter, selecting an undetected file in a large repository is a directory-by-directory hunt. This is the strongest Tier 2 item and the one most likely to be misjudged as polish.
- **Indent guides.** VS Code ships them at 8px indent with hover-revealed guides. At thirteen levels deep, which this product has measured, tracing a row to its parent is otherwise guesswork.
- **Sticky ancestors while scrolling.** VS Code's tree sticky scroll on by default capped at 7, and GitHub's sticky file headers. In a tree where the user scrolls a long expanded branch, losing the parent chain off the top is a real orientation cost.
- **Per-row annotation carrying why a file was proposed**, already built, and GitHub's in-tree comment and warning indicators confirm the shape: the reason belongs on the row, not in a legend.
- **A count of what is below the fold**, matching the grid's repository count and GitHub Desktop's `"N changed files"` header.
- **A scroll-edge divider that appears only once content is scrolled under the fixed chrome**, per Material and Apple's hard-variant scroll edge effect — the detail that makes fixed chrome read as deliberate rather than as a stuck bar.
- **Real modal semantics** — `role="dialog"`, `aria-modal`, a focus trap, Escape to cancel, and initial focus on the least destructive control. The surface is modal in behaviour already; it simply does not say so.

## Tier 3 — advanced, out of scope, with reasons

- **Compact folder chains** (VS Code's `explorer.compactFolders`, GitHub's compound rows). Genuinely valuable at depth, and already an open thread in [adopting.md](../../repo-layer/adopting.md). Refused for now for the reason that thread names: a compressed row's **checkbox scope becomes ambiguous** once a folder checkbox means something specific and safety-critical, and VS Code's own experience shows a compressed row needs per-segment handling for click, rename, drag and multi-select. The cost lands squarely on the one invariant that guards against breaking a user's build.
- **Virtualization.** Refused because the measurement already removed the need: a collapsed directory costs one row, and the branches that stay collapsed are precisely the enormous ones, since nothing preselects them open. GitHub's own virtualization mode disables in-browser Find as a stated cost, which is a poor trade for a surface that wants a filter.
- **A tree/list view toggle** (Fork, `scm.defaultViewMode`). The whole point of this surface is that the repository is drawn *as itself*; a flat list is the thing the repo-layer work deliberately removed, and reintroducing it as an option would reopen a settled concern.
- **Recursive Option-click expand-all** (Finder) and the APG's optional `*` **expand-siblings**. Both are real accelerators, and both are refused for the same reason: on a 42,123-row repository they are a foot-gun that lands thousands of rows in the document in one keystroke, defeating the bound that makes the surface work at all.
- **Per-hunk or per-line granularity** (Sublime Merge, Tower). This surface selects whole files by definition — Seal manages files, not regions of them.
- **A status-letter badge vocabulary** (VS Code's M/U/A/D). The two-channel model is settled: accent for management state, dimming for out of scope, and no badge at all. A third channel of coloured letters would be exactly the clutter the elegance-and-minimalism standard rules out.
- **Multi-select by Ctrl/Cmd-click and Shift-click ranges** over rows, and the APG's optional Shift+Arrow and Ctrl+A. Refused because this tree has **no row-selection axis to extend** — selection here means "checked for management", and `Ctrl+A` over a repository would check everything, which is the precise catastrophe the folder-scoping invariant exists to prevent.
- **Persisting expansion, filter text or scroll position** between visits. Foreclosed by the memory-only webview, exactly as route and sidebar state were, and expansion is computed on arrival by design.
- **A drag-resizable tree pane** (GitHub's 2026 rebuild). There is no second pane here to trade width with.
- **A progress bar over the scan.** Refused on NN/g's own threshold: the scan measured 0.09 seconds on a 42,123-row monorepo, which is an order of magnitude below the 10-second line where a percent-done indicator earns its place.

# States

The surface is one surface in one visual language whatever it holds. The fixed header and fixed footer are present in **every** state below, because they are the frame rather than the content — the state changes what sits in the scrolling region between them, never the shape of the surface.

**Scan running** — the state that **currently cannot exist**, and the most consequential gap in the enumeration. The scan is awaited before the overlay opens, so the user gets no acknowledgement that their folder choice registered; they look at the previous screen. The fix is structural rather than cosmetic: the **overlay must open first and scan second**, holding the repository path in its header from the moment it opens. The scrolling region then holds **skeleton rows** in the tree's own shape and rhythm, reusing the grid's existing `.skeleton` primitive with its `prefers-reduced-motion` handling, marked `aria-busy`. The footer is present with its confirm control disabled, because the frame does not change between states. Against NN/g's limits: the measured scan is 0.09s, so the skeleton must be **delayed by roughly 250ms** — below that the operation completes and a flashed skeleton is *"more visual noise than reassurance"*. The state exists for the slow disk, the cold cache and the network volume, not for the measured case.

**Scan failed** — also cannot currently exist: a rejected scan never opens the surface and falls to the generic problem banner on the previous screen, so the user's folder choice evaporates with an error attached to somewhere else. The overlay must open and **own its own failure**: the scrolling region states that Seal could not read the folder, in the danger treatment, as an `alert`, with the path it tried and a **Try again** control — the grid's error state is the in-house pattern, and it also says the recovery from where the user is standing. The footer's Cancel remains; the confirm control is disabled.

**Nothing recognised** — the scan succeeded and found no probable secrets. This is **not an empty state**: the repository is still drawn in full, and the user's job simply becomes choosing rather than reviewing. Today it is a grey sentence beside a tree, which is the same language mismatch the grid's rebuild removed. It becomes the tree with **nothing checked, nothing expanded beyond the roots** — since expansion follows preselection and there is none — and the footer's confirm control disabled until the user checks something. The absence of a proposal is legible from an unchecked tree; a sentence saying so is the prose the rule disallows.

**Repository with no files** — a genuinely empty folder. The scrolling region holds the tree with **one row, the repository root, and nothing under it**. Distinct from the state above and it must not borrow its language: nothing recognised means Seal has no opinion, no files means there is nothing to have an opinion about. The footer's confirm control is disabled with nothing to select.

**Already fully managed** — a rescan of a repository where every candidate is already managed. Every detected file draws its existing *already managed* treatment, disabled and unselectable, and **nothing is newly checked**, so the confirm control starts disabled. The surface must not read as "nothing found" — the tree is populated and every row is accounted for; the user simply has nothing new to accept. The footer's confirm control becomes available the moment the user checks an undetected file, which is the legitimate reason to rescan a fully-managed repository.

**Ordinary populated** — the case the surface is built for. Detected files checked and annotated with their reason, their ancestor chains expanded, everything else collapsed to one row per directory, undetected files dimmed and selectable, pruned directories inert and marked. The footer states the count.

**Enormous repository** — the 42,123-row case. Structurally already handled, and the design's job is to not break it: a collapsed directory renders none of its children, the branches holding no candidates are exactly the ones that stay shut, and nothing virtualizes because nothing needs to. What this state adds is the **count in the header** so the size of the repository is a stated fact rather than an inference from a scrollbar, and it is the state that makes the filter valuable rather than merely nice.

**One** — a repository with a single detected file. No special layout; the tree draws its one expanded chain and the footer reads *Manage 1 file*, singular, as it already does.

**Forbidden or unavailable** — a folder Seal cannot read for permissions reasons rather than a scan error. Reached on macOS whenever the chosen folder sits inside a TCC-protected location. It renders as the scan-failure state with the permission stated as the reason, because the user's available act is the same one: a different folder, or granting access and retrying. Not silently disabled, and not collapsed into a generic failure.

# Best-practice rules

1. **A row that draws `cursor: pointer` responds to a click.** No row on this surface is inert while advertising that it is not. A row that genuinely cannot act — a pruned directory — draws neither the pointer cursor nor a twisty.
2. **A pointer click never changes what the operation will act on, except on the checkbox.** The checkbox is the only mouse target that alters the selection. This is GitHub Desktop's split, and it is stricter here because the operation queues files for encryption.
3. **Expansion and selection stay separate axes** in every input mode — pointer, keyboard and assistive technology. Browsing must never queue a file.
4. **A folder's checkbox reaches only the detected candidates beneath it, never every file.** No affordance anywhere on the surface — not a filter, not a keyboard accelerator, not a select-all — may widen a bulk selection past the detected set.
5. **The chrome is fixed and the tree is the only scrolling region.** The repository identity and the two actions are visible at every scroll position, in every state.
6. **The primary action names the operation and counts its objects**, so the blast radius is legible before the click rather than after.
7. **The divider between the fixed chrome and the tree appears only when content is scrolled beneath it**, per Material and Apple's scroll edge effect. Chrome that draws a permanent border when nothing has scrolled reads as a stuck bar.
8. **A collapsed directory renders none of its children**, in every state including while filtered. A tree that builds every row and hides them with styling pays the whole 42,123-row cost invisibly.
9. **A filter changes what is visible, never what is selected.** When cleared it restores the expansion the user had before it was typed. This is the standing requirement in [adopting.md](../../repo-layer/adopting.md) and it is absolute.
10. **The surface never states a fact it does not have.** Scanning, failed, empty-of-candidates and empty-of-files are four different things and are never collapsed into one screen.
11. **`aria-checked` only, `mixed` on partially covered folders, and no `aria-selected` anywhere.** The APG calls a tree carrying both *"extremely rare"*, and emitting `aria-selected="false"` on every row makes a screen reader announce "not selected" on all of them.
12. **Initial focus goes to the least destructive control**, per the APG's high-consequence guidance, and Escape cancels without confirming.
13. **No sentence sits in the layout.** The assurances this surface owes — that confirming encrypts nothing, that files stay where they are, that a rescan changes nothing already managed — live behind the info affordance the user chose to open. A sentence explaining the tree would be evidence the tree had failed to explain itself.
14. **A loading treatment is delayed past the point where it would flash**, and never becomes a percent-done bar for an operation measured in tenths of a second.

# Synthesis / proposal

Build a **full-window modal surface with three bands** — a fixed header, a single scrolling tree, and a fixed action bar — in the family's existing tokens, replacing the centred flowing column.

## The shape

The surface fills the window: **`.manage`'s `max-width: 72rem` and centring are dropped, and `.tree`'s `max-height: 26rem` is dropped**. The surface becomes a three-row grid — `auto` header, `1fr` tree, `auto` footer — at full window height, so the tree claims every pixel the chrome does not. At the default 1100×720 window that takes the tree from 416px to roughly 620px, from about 14 visible rows to about 22, and it keeps scaling on a large display where the current cap simply wastes the extra height.

It renders **inside the shell rather than instead of it**, so the title bar survives with its drag region, its theme control and its lock. This fixes a defect the owner did not name: today the surface replaces the whole window, leaving the macOS traffic lights on undraggable bare content. The breadcrumb trail is not extended into this surface — it is a modal act over an altitude, not a fourth altitude — and the surface declares what it already behaves as: `role="dialog"`, `aria-modal="true"`, `aria-labelledby` on its heading, a focus trap, Escape as Cancel, and initial focus on the **least destructive control**, which is the tree itself rather than the confirm button.

**Header**, fixed, raised, at `--radius-xl` where it meets the surface edge: the heading *Seal in `<repository>`*, the existing toggletip beside it carrying the assurances, the full repository path in monospace and dimmed, and the **repository's row count** as the stated fact that makes an enormous repository legible. On the right, the **filter field** — the toolbar's exact pattern from the grid, `search` icon inset at `0.65rem`, `max-width: 22rem`, `--radius-md`.

**Tree**, the only scrolling region, `overflow-y: auto`, no border of its own — the header's and footer's scroll-edge dividers bound it instead, and they appear **only when content has scrolled beneath them**.

**Footer**, fixed, raised, mirroring the family's existing `.batch` bar at the files altitude, which already establishes exactly this idiom: a count at the leading edge and a button naming the operation with its count at the trailing edge. Cancel sits **left of the confirm button**, confirm rightmost and bound to Return, per macOS convention and the family's own `Confirm` component. The confirm button keeps the count it already carries and gains the destination the same way GitHub Desktop's does: **`Manage N files in <repository>`**, truncating the repository name rather than the count. Disabled at zero selected.

## What a click does — the recommendation

This is fault F1 and the survey answers it cleanly, but the answer is not the obvious one, because **a bare row click here already selects** on folders that have candidates, and that behaviour is asserted by tests. So the fix is not merely to give inert rows a response; it is to make one rule true of every row.

- **A click on a folder row expands or collapses it.** This is VS Code's default (`workbench.tree.expandMode: singleClick`), it is the user's stated mental model — *click a folder to open it* — and it is permitted by the settled contract, since **expansion is not selection**. It makes the whole row a large, forgiving target for the one act a user performs constantly while browsing.
- **This replaces row-click-to-select on folders.** Selecting a folder's candidates becomes the checkbox's job **only**. This is the change that makes the rule uniform, and it is the one the prior art insists on most consistently: GitHub Desktop routes the mouse click away from inclusion entirely, GitKraken reserves the row click for viewing, and Finder never lets a row click alter anything but selection-for-viewing. It is also the safer rule by the standard this surface is judged on — a click that could queue a directory's secrets for encryption should require aiming at a checkbox, not merely landing anywhere on a 600px-wide row. Three existing tests assert the current behaviour and must be updated to drive the checkbox; that is a deliberate, recorded change to a *presentation* behaviour, not to the tree's contract, which never specified which pointer target performs the selection.
- **A click on a file row does nothing to the selection either.** For symmetry and safety it toggles nothing; the checkbox toggles. A file row has no children, so a click on it is a no-op that focuses the row — which is what Finder's row click does, and it keeps rule 2 uniform across both kinds of row.
- **A click on the twisty expands or collapses**, unchanged, stopping propagation, and remaining a single-click target regardless of what the row does — VS Code preserves exactly this even under double-click expand mode.
- **A click on the checkbox toggles selection**, unchanged, stopping propagation. On a folder it reaches only the detected candidates beneath it.
- **A pruned or unwalked directory** draws no twisty, no checkbox, and **no pointer cursor** — the `cursor: pointer` currently on every row is removed from these. The row is an answer, not a door, and it should not look like one.
- **The keyboard model is untouched.** Space toggles the focused row's checkbox, arrows move and expand, Enter's default action on a parent is to open or close it, per the APG. Keyboard selection therefore stays on Space alone, which matches GitHub Desktop's separation of the keyboard path from the mouse path.

## Density and scannability

Rows keep a single-line height and gain a **fixed row height** rather than one derived from content, so the rhythm holds at depth and no annotation can grow a row taller than its neighbours — the same rule the grid's tiles adopted. Indent goes from the current `1.1rem` per level to VS Code's measured **8px**, which at thirteen levels reclaims roughly 60px of horizontal space, with **indent guides** drawn at each level so a deep row traces to its parent. File names stay monospaced and directory names stay proportional, which is the existing distinction and a good one — it makes the two kinds of row separable at a glance without a badge. The reason annotation and the *already managed* note stay dimmed at `0.78rem` on the row's trailing edge, and truncate rather than wrap. **Sticky ancestors** pin the parent chain of the topmost visible row, capped at a small number the way VS Code caps at 7 and at a fraction of the tree's height, so scrolling a long branch never loses the context of which directory it is in.

## Finding a file — the filter

**Recommended, and it is table stakes for this surface** rather than a refinement, though it is the second thing to build rather than the first. The standing thread in [adopting.md](../../repo-layer/adopting.md) asked whether locating a known file among collapsed branches is awkward enough to want one, and the shape of this surface answers it: expansion follows the *detected* files, so every file the scan did **not** detect — which is the entire reason undetected files are selectable at all — is reachable only by manually opening the chain to it. In a 42,123-row repository that is a directory-by-directory hunt for a file the user can already name. The affordance exists precisely for the case the tree is worst at.

Its required behaviour, binding:

- It filters **the tree**, matching case-insensitively on the **path**, not only the leaf name, so a folder match reveals what is under it — GitHub's documented behaviour.
- It **expands to reveal matches** and prunes non-matching branches, keeping matched rows' ancestors for context — VS Code's filter mode.
- Clearing it **restores exactly the expansion state that was in force before the first keystroke**, which must therefore be captured on entry and not recomputed.
- It **never touches the selection**, in either direction. A row that scrolls out of the filter keeps its checkbox state, and confirming while a filter is active acts on the whole selection rather than on what is visible — with the footer's count continuing to state the true total, since the count is the safety statement and must not narrow to the view.
- With no match, the tree region says so in the tree's own language and offers to clear the field — a state, as the grid's no-match state is, not an explanation.

## Load-bearing versus rounding out

**Load-bearing** — the surface is not fixed without these. The three-band full-window shape with the tree as the only scrolling region. The fixed header carrying the repository identity and the fixed footer carrying both actions and the count. The uniform row-click rule, with expansion on the row and selection on the checkbox only, and the pointer cursor removed from genuinely inert rows. The overlay opening **before** the scan so that a loading state and a failure state can exist at all. The four missing states — scanning, failed, nothing-recognised, no-files — in the surface's own language.

**Rounding out** — real improvements that can be staged behind the above. The filter, which is the first thing to add once the frame is right. Sticky ancestors. Indent guides and the 8px indent rhythm. The scroll-edge dividers. The row count in the header. The repository name on the confirm button. Modal semantics are a small change that should ride along with the frame rather than wait, since the surface already behaves modally and merely fails to say so.

## Out of scope, carried forward

Everything in Tier 3, with its reason. The three most likely to be re-proposed, so they are named here as decisions rather than oversights: **compact folder chains**, refused because a compressed row's checkbox scope collides with the folder-scoping invariant, and left as the open thread it already is; **virtualization**, refused because collapsed directories already bound the surface and virtualizing would cost the filter; and **recursive expand-all in any form**, whether Option-click or the APG's `*`, refused because a single keystroke landing thousands of rows in the document defeats the one rule that makes a 42,123-row repository tractable.

# Open threads

- **Whether the header carries the repository's total row count or its candidate count, or both.** The row count states the size of what the user is looking at; the candidate count states the size of the proposal, which the footer already counts once selection is untouched. Two counts in one header risks the clutter the standard rules out, and which single number is more useful wants seeing the built surface.
- **Whether the filter's field belongs in the fixed header or above the tree inside the scrolling region.** The header is the family's toolbar pattern and keeps the field reachable at any scroll position; putting it in the header also means it survives every state, which the scanning and failure states may not want. Recommended in the header, but the interaction with those two states wants driving rather than deciding on paper.
- **The sticky-ancestor cap.** VS Code uses 7 items and roughly 40% of view height. This tree's rows are shorter and its window smaller, so the right cap here is probably lower; it wants measuring against the 560px minimum window height rather than copying the number.
- **Whether a rescan of a fully-managed repository should open at all**, or whether the entry point should state that there is nothing new before spending the user's attention. The state is designed above either way, but the question is a level up from this surface and touches the grid's ellipsis menu.
- **Path compression for single-child chains** remains open exactly as [adopting.md](../../repo-layer/adopting.md) left it, and this research does not settle it — it only adds the reason it is riskier here than in VS Code, which is that a compressed row's checkbox scope is ambiguous in a tree whose folder checkboxes carry a safety invariant.
