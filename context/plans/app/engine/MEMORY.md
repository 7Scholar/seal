# Memory

## 2026-07-20 — The scrypt work factor is pinned explicitly, never left to the crate default

Sealing always calls `age::scrypt::Recipient::set_work_factor` with an explicit value rather than using `Encryptor::with_user_passphrase` or an unset recipient. **Why:** the crate's default work factor is not a constant — it is auto-calibrated at runtime by timing scrypt to hit roughly one second, so it varies with the machine, its load, and the build profile (a debug build calibrates far lower than release). A sealed file's cost would then be an accident of the machine that produced it. **Mistake it prevents:** dropping the explicit call as redundant, which silently makes the format's security parameter machine-dependent and lets a slow or loaded machine seal a file at a weak work factor. Unsealing separately caps accepted work with `Identity::set_max_work_factor` so a hostile file cannot force an enormous derivation.

## 2026-07-20 — The replace temp file lives in the target's own directory, never in a temp dir

The scratch file a seal or unseal writes before renaming is created in the same directory as the target file, not in `/tmp` or any system temp location. **Why:** `rename` fails with `EXDEV` across filesystems, so a temp file elsewhere cannot atomically replace the target. This passes local testing on machines where the temp dir happens to share the target's volume — verified here that `/private/tmp` and the working tree sit on the same APFS volume — and then fails for any user whose repo is on an external drive, a separate volume, or a network mount. **Mistake it prevents:** "tidying" the temp file into the system temp directory, which looks cleaner, tests green locally, and breaks in the field.

## 2026-07-20 — Metadata is captured and restored explicitly across the replace

Seal and unseal capture the target's mode and xattrs before writing and restore them onto the replacement before the rename, and the temp file is created mode `0600`. **Why:** `rename` installs a new inode, so everything inode-resident is replaced by the temp file's own attributes. Measured: a `0600` secrets file came out `0644` after a naive replace, with its xattrs gone — sealing a secret would silently widen it to world-readable. **Mistake it prevents:** treating the metadata capture/restore as incidental bookkeeping and dropping it during a refactor, which reintroduces a permission-widening security regression that no test of the file's *contents* would catch. ACLs and birthtime are known **not** to survive this sequence and are out of scope.

## 2026-07-20 — Sealing does not revoke access through descriptors already open

A process that opened a file before it was sealed keeps reading the original plaintext afterwards, through its existing descriptor, for as long as it holds it. Verified: after a seal, the orphaned inode reported `st_nlink` of zero — absent from every directory listing — while the pre-seal plaintext remained fully readable through the held descriptor. **Why:** replacement swaps the directory entry to a new inode; it does not touch the old inode, which survives as long as any descriptor references it. **Mistake it prevents:** treating a completed seal as the moment the plaintext became unreachable, and so telling the user a file is protected while an editor or agent that opened it earlier still reads it at will. The seal is a guarantee about future opens, not about existing ones.

## 2026-07-20 — Interoperability tests skip for contributors but must fail loudly in continuous integration

The interoperability tests skip themselves when the stock `age` binary is absent, except when an environment variable marks the run as one that requires them — which the continuous-integration job sets. **Why:** the skip exists so a fresh clone is green without installing anything, but that same skip would let the interoperability job report success while verifying nothing if its install step ever broke, and that job is the only thing proving the guarantee the whole format choice rests on. Verified: without the variable a missing binary skips silently; with it, the run fails naming the reason. **Mistake it prevents:** removing the variable or the assertion as redundant ceremony, which converts the single most important guarantee in the project into a test that passes whether or not it ran.

## 2026-07-20 — The work factor is range-checked before it reaches the age library

Sealing validates the requested work factor against the accepted range and returns an error before calling the library. **Why:** the library asserts the factor is within its own bounds and **panics** outside them rather than returning an error — measured, a factor of 200 aborts the thread. A panic inside a library call takes down whatever is running it, so a caller passing a bad value would crash the desktop application instead of being told no. **Mistake it prevents:** removing the check as redundant because the value "always comes from a constant" — it does not, since the re-seal operation accepts a work factor from its caller, and the panic surfaces as a crash rather than a failed operation.

## 2026-07-20 — The lock file is never deleted, not even when releasing the lock

Releasing a file lock closes the handle and leaves the lock file in place. **Why:** the lock lives on the open file, not on the name. Deleting the file while still holding it lets another process create a fresh file at the same path and lock *that* inode, so two writers proceed at once — measured, and it defeats the entire purpose of the lock. Deleting it after closing is no better, because the same window exists between close and unlink. **Mistake it prevents:** removing the leftover zero-byte lock file to keep the directory tidy, which silently converts mutual exclusion into the appearance of it. A stray hidden lock file is harmless; a broken lock corrupts a user's secrets.

## 2026-07-20 — A sealed file's work factor is read through the armor decoder, never from raw lines

Reading the work factor out of a sealed file goes through the armor-decoding reader rather than scanning the file's lines for the stanza. **Why:** in an armored file the entire age header is base64-encoded inside the armor framing, so the `-> scrypt <salt> <factor>` line simply does not appear as text — a raw line scan finds nothing and every read fails. It only looks workable because the equivalent scan does work on a binary age file, which is the encoding Seal never writes. **Mistake it prevents:** "simplifying" the header read to a plain line scan, which passes any test using binary fixtures and fails on every file Seal actually produces.

## 2026-07-20 — Dependencies are optimized even in debug builds

The workspace sets an optimization level for all dependencies in the dev and test profiles while leaving Seal's own crates unoptimized. **Why:** the whole engine rests on a deliberately expensive key derivation, and an unoptimized build of it is roughly fifty times slower — measured, the format suite alone went from about seven and a half seconds to under two tenths. **Mistake it prevents:** removing the profile overrides as unnecessary tuning, which silently turns a fast test suite into one slow enough that contributors stop running it, while leaving our own code debuggable is what makes the setting free.

## 2026-07-20 — A symlinked target is refused, never followed

Replacement refuses outright when the target path is a symbolic link, rather than sealing through it. **Why:** the sequence renames over the *path*, so following the link would destroy the link, write a regular file in its place, and leave the real secret sitting unprotected at the link's destination — measured, with the metadata additionally captured from the destination while applied to the replacement. A user would believe they had sealed their secret when they had sealed a copy and broken their setup. **Mistake it prevents:** "supporting" symlinks by resolving the target first, which looks like an improvement and silently turns the one file the user cared about into the one file left in the clear. Refusing is the correct behavior; a caller that wants the destination sealed must name the destination.

## 2026-07-20 — A bare filename's parent is the empty path, not absent

Resolving a target's containing directory treats an empty parent as the current directory, not merely an absent one. **Why:** `parent()` on a bare relative filename returns `Some("")` rather than `None`, so the obvious `unwrap_or(".")` never fires and the directory sync is attempted on the empty path, which fails. The replacement still succeeds, so the failure surfaces only as a mislabeled error after everything committed — the durability guarantee is silently not delivered. **Mistake it prevents:** simplifying the resolution back to `parent().unwrap_or(".")`, which reads as obviously equivalent and quietly drops the directory sync for every relative-path caller.

## 2026-07-20 — External-replacement detection needs the whole identity tuple

Detecting that a sealed file was replaced by something else compares device, inode, modification time, and size together — never one field. Verified: an editor's atomic save changed inode, mtime, and size; a same-length in-place overwrite changed mtime only, leaving inode and size identical. **Why:** inode alone misses an in-place overwrite, and mtime alone cannot distinguish an ordinary edit from an identity swap; each field covers a case the others miss. **Mistake it prevents:** simplifying the fingerprint to "just compare mtime" or "just compare inode," which silently stops detecting the case the dropped field covered — and the case being missed is a sealed file quietly replaced by plaintext.

## 2026-07-20 — Filesystem watches target the parent directory, never the file

Any filesystem watch this application establishes targets a containing directory, never an individual managed file. **Why:** whether a file-level watch survives the file being replaced depends on the backend, and it does not survive on all of them. The default macOS backend is path-based and keeps reporting through a rename-replacement; the alternative macOS backend and Linux's are inode-bound, where a rename orphans the watch permanently — measured as one event followed by silence. A directory watch is correct on every backend, is the only way to observe the watched entry itself being deleted, and shows the temp file being created and renamed into place, which is the whole signature of a replacing save rather than its tail. **Mistake it prevents:** confirming a file-level watch works on macOS, concluding it is sufficient, and shipping a watcher that silently stops detecting replacements on Linux — the exact event it exists to catch. Note that watching is a supplement to scanning rather than the primary mechanism (see the registry plan): Linux charges one watch per directory against a per-user limit that a single dependency directory can exhaust.

## 2026-07-20 — Unsealing wraps input in `ArmoredReader` regardless of format

The unseal path always constructs the decryptor over `age::armor::ArmoredReader`, never over the raw reader. **Why:** `ArmoredReader` passes binary age files through transparently, so the single wrapped path reads both armored and binary input; a decryptor constructed on raw bytes rejects armored input with `DecryptError::InvalidHeader`. **Mistake it prevents:** removing the wrap as unnecessary when sealing happens to emit binary, which breaks reading any armored file — including files produced by standard `age`/`rage`, which Seal must stay compatible with.
