# Intent

## What & why

The sealing engine is the cryptographic heart of Seal and the seam every other concern consumes: it turns a plaintext file at a path into a sealed file at that same path and back, under the constraints the root Approach fixes — standard age v1 format with an scrypt passphrase recipient via the `age` Rust crate, one master password by default with optional per-repo overrides, and passwords that exist only in the user's head. It owns the handling of secret material in memory (passphrases, file keys, plaintext buffers) and the semantics behind the app's unlocked session and the CLI's per-operation prompt. It is a pure Rust library with no Tauri dependency, so its behavior is fully testable without a runtime. It is done when sealing, unsealing, password verification, and password change work exactly as specified, with the failure and edge behavior (wrong password, corrupted file, partial writes, already-sealed input) defined and tested.

## Approach

The engine is a plain Rust library crate with no dependency on Tauri, on the registry, or on any UI. Its whole surface is: classify a path, seal a path, unseal a path to memory, unseal a path in place, and verify a passphrase. Everything else in Seal is a consumer of these operations.

### Sealed-file format

A sealed file is a standard age v1 file carrying exactly one scrypt passphrase stanza, written **ASCII-armored** — the `-----BEGIN AGE ENCRYPTED FILE-----` framing. Armor is chosen because a sealed file must survive the life of a text file in a repo: it stays line-oriented for tools that assume text, remains diffable and greppable as text, and is visibly, self-evidently sealed to a human who opens it. The size cost is irrelevant at env-file scale. No Seal-specific header, marker, or metadata is added: byte-compatibility with standard `age`/`rage` is a guarantee of the format, so any sealed file is recoverable with the password and stock age tooling even if Seal itself is gone.

The scrypt work factor is **always set explicitly** by the engine and never left to the crate's runtime-calibrated default. The engine defines one work-factor constant for newly sealed files, chosen so a derivation costs a few hundred milliseconds on typical current hardware, and records nothing about it outside the file — the age format already carries the factor in its stanza, so unsealing a file sealed under an older constant keeps working. Unsealing caps accepted work via the identity's maximum-work-factor setting, so a hostile or corrupt file cannot force an unbounded derivation.

### Classification

Classification answers "what is this path?" without a passphrase and without reading more than a file's opening bytes: **sealed** (an age file, armored or binary), **plaintext** (anything else), or **absent**. It reads only the head of the file, so it is cheap enough for the registry to run across every managed file on demand. The engine treats binary age files as sealed even though it never writes them, because a user may seal a file with stock age tooling and Seal must recognize it. Classification never decrypts and so never needs a passphrase; a file that is sealed but unopenable by the current passphrase still classifies as sealed. For a sealed file it also reports the **work factor** read from the file's own stanza, so a consumer can surface a file sealed weakly — by an old Seal version, by stock age on a slow machine, or by a hostile party — as something to re-seal. Unsealing enforces both a maximum accepted work factor (against a file engineered to force an enormous derivation) and a minimum below which a file is reported as weakly sealed.

Classification operates on an **already-open file handle**, with a path-taking convenience wrapper for the registry's bulk scan. This matters for correctness, not ergonomics: an operation that classifies by path and then re-opens the file to act on it can be raced between the two opens, so a guard promising "seal refuses an already-sealed file" would not actually hold. Every operation opens the target once and classifies from the same handle it goes on to read.

Bulk classification over many paths is its own operation returning a per-path result, since one unreadable file among two hundred must not fail the sweep.

### Operations and their invariants

`seal` requires the target to classify as plaintext and refuses a file that is already sealed, so that a double-seal can never silently produce doubly-encrypted content. `unseal_to_memory` returns the plaintext to the caller — the CLI's resolution path and the UI's editor both use it — and leaves the file on disk untouched, sealed. `verify` attempts the header key-unwrap only and reports whether a passphrase opens a given sealed file, without producing plaintext; its cost is one full derivation by construction, with no early-out, and it is never exposed unauthenticated or unthrottled to anything outside the app.

Whether the engine offers an operation that leaves plaintext on disk permanently, and in what form, is **an open product decision** — see `QUESTIONS.md` at the root. The engine's write path supports it either way; what is undecided is whether Seal should offer it at all, and that is not a decision the engine layer gets to make quietly by exposing the verb.

Every operation returns an **observed post-state** — the resulting classification plus a file identity fingerprint (device and inode, size, and modification time) — rather than nothing. This is what lets a consumer detect that a file it sealed was later replaced by something else: the registry records the fingerprint at seal time and a mismatch on re-check means the file's identity changed underneath it. That detection is not a nicety, because the most likely real-world way a seal is destroyed is an editor that had the file open saving over it afterwards.

Passphrase-taking operations accept an **ordered list of candidate passphrases** and report which one opened the file, rather than a single passphrase and a yes/no. This follows directly from the per-repo override model: with a master password and an optional override in play, a single-passphrase signature makes four genuinely different situations indistinguishable — the user typed the master when the file needs the override, typed the override for a file sealed before the override existed, typed the override for a file moved in from another repo, or simply typed the wrong thing. Reporting only "wrong passphrase" would tell a user their password is wrong while they are typing a completely correct one, which for a product with no recovery path is the worst possible false accusation. The engine stays free of the registry — the caller decides *what* the candidates are — but the shape at the seam is plural. Candidates are capped in practice at a small number, since each costs a full derivation.

Every operation that writes is **atomic and identity-preserving**, in this order: capture the target's mode and extended attributes; create the replacement in the target's own directory as a dotfile with a random suffix, opened exclusively at mode `0600`; stream the transformed content into it; restore the captured mode and extended attributes onto it; flush it to durable storage (`F_FULLFSYNC` on macOS, falling back to an ordinary sync where unsupported); rename it over the target; sync the containing directory so the rename itself is durable. A guard removes the temp file on any failure or panic, so a failed operation leaves the user's directory exactly as it was. The temp file lives in the target's directory because rename cannot cross filesystems; this is a correctness requirement, not a preference. ACLs and creation time are known not to survive an inode replacement and are explicitly out of scope; the plan states this rather than leaving it to be discovered.

The crash contract that follows: at every instant the target path holds either the complete old file or the complete new one, never a partial write, and the plaintext is never destroyed before the sealed replacement is durable. The failure mode a crash can produce is a leftover temp file, which is inert and removable.

**Durability is directional, and this is a security property rather than a performance tuning knob.** Writing ciphertext flushes hard, because losing a seal to a crash is the failure the contract exists to prevent. Writing plaintext to disk does the opposite: it deliberately does *not* force the data to the physical medium, because durability of plaintext is an anti-goal for a product whose purpose is that plaintext should not persist. The write path therefore takes durability as an explicit parameter rather than always flushing, and the two directions pass different values.

**Concurrent operations on one path are serialized by an advisory lock** held across the whole classify-and-replace sequence, not left to last-writer-wins. Atomic replacement alone prevents a corrupt file but gives no serializability: two processes — the app and the CLI are separate processes, so this is reachable in normal use — can both classify a file as plaintext, both seal it, and the second rename wins. With per-repo overrides that means a file can end up sealed under a passphrase the user's mental model says is wrong, which looks exactly like data loss and cannot be diagnosed after the fact. The lock is a sibling lockfile acquired before classification and released after the rename; a caller that cannot acquire it is told the file is busy rather than proceeding.

**The sequence's syscall boundary is an explicit seam**, not inlined calls. Each step that can fail — creating the temp file, streaming, restoring metadata, flushing, renaming, syncing the directory — goes through a small interface with a real implementation and a fault-injecting test implementation. This is dictated by the verification requirement below: the crash contract is the engine's most load-bearing promise, and a design whose only failure hook is the content-write closure can exercise exactly one of the seven steps. Without the seam the contract ships either untested or tested only where it happens to be reachable. The metadata captured and restored across the replace is an opaque platform-typed value in the interface rather than a concrete mode-and-xattrs pair, so the eventual Windows implementation — which has none of those concepts and uses a different replacement primitive entirely — is a new implementation of the same seam rather than a rewrite of its callers.

Content is streamed between file handles rather than buffered whole, so a large managed file does not require memory proportional to its size. `unseal_to_memory` is the deliberate exception, since its caller wants the bytes.

### Passphrase model

The engine resolves which passphrase applies to a file but never stores one. Resolution is: the repo's override passphrase if that repo has one, otherwise the master passphrase. The engine is told the resolved passphrase by its caller; it does not consult the registry itself, keeping it free of that dependency. Because a per-repo override means a file's ciphertext is bound to whichever passphrase sealed it, changing a repo's passphrase is not a metadata edit — it is a re-seal of every file in that repo, which the engine exposes as an explicit operation with a partial-failure report rather than an all-or-nothing promise it cannot keep across many separate files.

Passphrases cross the API as the secrecy crate's protected string type and derived key material is zeroized on drop. Plaintext buffers returned to callers are the one place secret material leaves the engine's control, and the API hands them back in a zeroize-on-drop container so a careless consumer does not leave copies behind.

### Error taxonomy

Errors are a `thiserror` enum whose variants map to distinct user-facing outcomes, because the sanity-test confirmed the underlying library distinguishes these cases cleanly: no-candidate-passphrase-opened-it, not-a-sealed-file, corrupt-or-truncated sealed file, already-sealed (from `seal`), not-sealed (from the unseal operations), absent path, file-busy (the lock was held elsewhere), and an IO variant naming the failed step. Wrong passphrase and corrupt file are deliberately separate variants: conflating them would make the UI tell a user their password is wrong when their file is damaged. Error values never carry plaintext, passphrases, or key material, and the underlying library's error text is mapped to deliberate variants rather than passed through.

### What the engine is not responsible for

Two adjacent problems are named here because they are real, they will be discovered during implementation, and they belong to other layers. A **sealed file replaced from outside** — most likely by an editor that had it open when it was sealed and then saved over it — is detected by comparing the identity fingerprint the engine returns against the one recorded at seal time; the engine supplies the fingerprint, and the registry owns the recording, the re-checking, and the alerting. Writing plaintext into a **git-tracked path** is likewise not the engine's to police: the root Approach puts git state outside Seal's scope, and that reasoning holds for sealed files, but it does not extend to writing a production credential in the clear into a tracked path. That check belongs to the layer that knows about repos, and it is a requirement on the desktop application rather than an engine concern.

Re-sealing a set of files under a new passphrase is exposed as an operation over an explicit list of paths with a per-file report, not as a repo-level operation — the engine cannot enumerate a repo and has no concept of one. The caller owns the plan and, where the operation must be resumable, the journal.

### Verification

The engine is testable end-to-end without a Tauri runtime, and its test suite is part of what "done" means: round-trips across file sizes and content shapes; every error variant provoked deliberately; metadata preservation asserted explicitly, including the `0600`-stays-`0600` case that a naive implementation regresses; and crash-safety exercised by injecting a failure at **every** step of the replace sequence through the syscall seam, asserting in each case that the target is left wholly intact and no debris remains.

Standard-format compatibility is a claim tests must hold to, and it is verified two ways because the two catch different things. A committed corpus of **static test vectors** — files sealed by known-good stock tooling at known passphrases and work factors, including armored and binary, empty and large — gives hermetic regression coverage that runs anywhere with no external binary. Separately, tests against a **real, version-pinned `age` binary** in both directions catch forward-compatibility drift that fixed vectors never would. The live-binary tests are excluded from the default test run and live in their own continuous-integration job, because an open-source project whose test suite fails on a fresh clone for want of an external tool loses contributors; a contributor runs the vectors and gets real coverage, and the pinned job runs the rest.

Two of the properties above are invisible to ordinary assertions and are therefore called out as things to test deliberately rather than assume: that the plaintext write path does **not** force data to durable storage, and that no error value ever carries plaintext or passphrase material. The second is enforced structurally as well as tested — the error type's payloads cannot hold free-form text from the underlying library, since a library's error strings are the likely leak vector — because a test can only check the variants that exist today.

# Open threads

- The exact work-factor constant: pick by measuring a derivation on current hardware in release build during `format.md`, targeting a few hundred milliseconds. Decide the minimum-accepted floor at the same time, from the same measurement.
- Whether to offer the `RENAME_SWAP` variant on macOS to retain the original inode for a rollback window; the plain-rename sequence is correct without it, so this is an optimization to evaluate, not a requirement.
- Whether plaintext buffers should be locked into memory to keep them out of swap, or whether swap is declared out of scope and left to full-disk encryption. The threat model currently states the latter; revisit if locking proves cheap and reliable across platforms.
